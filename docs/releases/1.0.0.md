# SchemaHub {{SCHEMAHUB_VERSION}}

SchemaHub 1.0 is the first stable release of the human-and-agent schema-change
control plane and immutable schema-serving plane.

## Upgrade contract

- Source version: `0.9.0-rc.1`.
- Target version: `{{SCHEMAHUB_VERSION}}`.
- Migration set: the checksum-verified PostgreSQL baseline
  `202607210001_initial_schema.sql` and the versioned redb object encodings
  shipped by the candidate. SchemaHub applies the PostgreSQL migration before
  readiness; operators must not edit the SQLx migration ledger. The first
  ChangeRecord ledger operation backfills repository creation/status indexes,
  while the first project/repository catalog operation backfills active/all
  project and per-project repository name indexes. Each validated backfill and
  its durable completion marker commit atomically. Allow those first operations
  to finish before acceptance traffic.
- Mixed-version allowance: none. Drain and stop the candidate before starting
  1.0 against the same redb file or PostgreSQL schema. Do not run candidate and
  1.0 processes concurrently against one database.
- Rollback window: retain the pre-upgrade redb/PostgreSQL backup and the exact
  candidate image digest until stable acceptance finishes and the operator's
  rollback window closes. Database rollback is restore-based; do not delete
  migration rows or attempt a destructive down migration.

## Staging acceptance

The stable workflow accepts this release only after an independently reviewed
production-like staging run uses PostgreSQL, the intended external JWT/JWKS
provider, and the exact container digest below. The run must prove:

- delegated-agent authoring, independent human review, and policy-gated Apply;
- same-origin bundled-GUI root/deep-link serving, immutable hashed assets, and
  non-HTML unknown-BFF `404` behavior from the exact image;
- byte-identical immutable artifacts across restart and from the prior
  candidate;
- fail-closed handling of a corrupt durable artifact record;
- visible live and pinned `ListDependents` results without hidden-repository
  disclosure;
- current/next/removed/stale signing-key behavior and recovery; and
- backup restoration into a fresh PostgreSQL database.

`schemahub-staging-attestation.json` binds those results to the exact source,
container, and `schemahub-ga-readiness.tar.gz` digest. Both evidence artifacts
are included in the distribution SBOM and `SHA256SUMS`.
The versioned container tag is withheld until that attestation and the complete
checksummed release assembly succeed, then created from the accepted digest
without overwriting a different existing tag. The retained assembly's exact
file set and every checksum are reverified after download before publication.

## Compatibility changes

- `schemahub.v1` gRPC/protobuf is the public 1.x API compatibility surface.
  The unversioned `/api/*` routes remain a GUI-only BFF supported only with the
  bundled GUI from the same release.
- That version-matched BFF/GUI pair pages project and repository selectors over
  bounded Core catalog ranges. Opaque continuations reject cross-kind,
  cross-project, and cross-prefix reuse; project summaries no longer enumerate
  repositories for a count, and deep links use one bounded exact-prefix lookup.
- Repository dashboards page schema, branch, and tag projections with one
  repository/ref-bound token. Schema summaries and conflict counts stay on the
  first page's immutable commit even if the bookmark advances. Selected schema
  objects and repository-local names load in one tree traversal, avoiding
  per-schema full-tree scans; dependency totals are unique declared direct
  imports. Browser
  ChangeRecord lists use repository/status-bound pages over the same durable
  index as `schemahub.v1`; the bundled GUI requests both continuations
  explicitly.
- Native archives contain that exact production GUI under `schemahub-gui/`;
  the release container serves the same locked build from its HTTP root with
  explicit deep-link and immutable-asset behavior and no runtime code-viewer
  CDN dependency.
- ChangeRecord intent, executable edits, validation, reviews, conflicts,
  idempotent Apply receipts, commits, operation history, immutable revisions,
  and first-materialized artifacts are durable and auditable. `ListChanges`
  preserves its v1 order/filter/token contract while using bounded
  repository/status-index range reads; creates and lifecycle transitions
  update record/index state atomically and corrupt index targets fail closed.
- Project, membership, and repository mutations atomically append immutable
  typed before/after audit events and their ordered index entries with
  server-derived actors. Owners page that index through bounded backend range
  reads over gRPC or `schemahub project audit --json`; malformed or mismatched
  index records and missing event targets fail closed. Project-keyed
  cross-instance coordination preserves membership invariants under races.
- `ListProjects` and `ListRepos` preserve their v1 name order, filters, and
  opaque tokens while using bounded active/all catalog ranges. Resource creates
  and archive transitions update those indexes atomically; pre-index resources
  backfill once, and malformed cursors or corrupt catalog targets fail closed.
- `ListMembers` now has `page_size`, `page_token`, and `next_page_token`.
  Stable identity-ordered pages read only one bounded project-primary-key
  range, continue across inactive tombstones, and reject cross-project or
  malformed tokens. Pre-1.0 clients that assumed one unbounded response must
  follow the continuation; `schemahub project member list [--json]` does so.
- `ListBranches` and `ListTags` now have `page_size`, `page_token`, and
  `next_page_token`. Tokens bind ref kind, project, repository, and prefix;
  pages preserve lexicographical ref-name order and bounded response
  materialization. Pre-1.0 clients must follow the continuation;
  `schemahub branch list` and `schemahub tag list` do so automatically.
- Protobuf, FlatBuffers, and the advertised OpenAPI capability matrix are the
  supported schema formats. Whole-schema and advertised granular operations
  share the same format-agnostic Core publication, compatibility, reference,
  authorization, and conflict policy.
- Data producers and consumers can retain an immutable `SchemaRevision`,
  payload/closure digest, and source, descriptor, or generated binding used to
  encode or decode application data.
- The warning-clean FlatBuffers revision recorded under Provenance is part of
  the coordinated 1.0 compiler boundary.

## Security and dependency integrity

- Release CI requires the pinned Rust audit to report zero vulnerabilities and
  exactly the reviewed warning set, then audits the frozen GUI and
  workflow-demo pnpm graphs at Low severity.
- JWT signature verification uses the AWS-LC backend, including tested RS256
  JWK verification; the vulnerable RustCrypto RSA dependency is absent.
- Patched web transitive versions are locked. The sole pnpm advisory exception
  covers unused React Router server-side RSC APIs and is guarded by a
  client-only routing contract.

## Known issues

- OpenAPI code generation is outside 1.0; OpenAPI source, compatibility,
  dependency discovery, and immutable descriptor closure remain supported.
- The GUI authors executable whole-source replacement and deletion edits.
  Compiler-specific granular mutation builders remain CLI/gRPC workflows.
- Search remains repository-scoped. Cross-repository search is not supported.
- Reverse dependency discovery is bounded, direct, authorization-filtered, and
  snapshot-manifest based. It is not a global snapshot.
- There is no automatic cross-repository rewrite, transitive reverse
  traversal, or global multi-repository transaction.
- Supported external OpenAPI component refs are live/unpinned textual edges.
  Network URLs, arbitrary fragments, repository-root escapes, `$ref` siblings,
  and unsupported standalone reference shapes fail closed.
- SchemaHub stores schemas and immutable artifacts, not application records,
  and does not execute database migrations derived from user schemas.
